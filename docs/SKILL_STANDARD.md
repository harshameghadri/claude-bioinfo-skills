# Skill standard: model-neutral, tested, publishable

A skill in this repository must work for any capable model or agent harness, not only the one it was written with. The model only ever sees `SKILL.md` (and the files it points to) and a shell; everything that can be a tested program is a program. `python3 scripts/validate_skills.py` enforces the mechanical parts of this document and CI runs it on every pull request.

## 1. Layout

```
skills/<name>/
  SKILL.md            required; frontmatter + procedure (at most 500 lines)
  references/         long material, loaded only when needed
  scripts/            standalone programs and libraries
  tests/run.sh        required when scripts/ exists; offline; exit 0 = pass
  tests/fixtures/     small deterministic inputs (or generated by the tests)
```

`<name>`: lowercase letters, digits, single hyphens, at most 64 characters, equal to `name:` in the frontmatter.

## 2. SKILL.md

- Frontmatter: `name` and `description`. `description` is the trigger: what the skill does, then when to use it, with the words a user would actually type. At most 1024 characters, no angle brackets, no line that begins a new YAML key.
- Body: a numbered procedure with exact commands, then "Rules that prevent known failures", outputs, and how the skill is tested. State requirements (languages, packages, external programs) at the top.
- Write for a reader that has no other context: define every file, column and flag it mentions, give expected exit codes and what to do on failure.
- Every `scripts/...`, `references/...` or `tests/...` path named in the text must exist (the validator checks).
- Say what is NOT verified. A claim that was not tested (a live endpoint, a parameter chosen by judgement, a code path that needs a package missing in CI) is labelled as such in the skill.

## 3. No vendor-specific vocabulary

Skill text must not name one harness's tools or paths: no tool names such as "use the Bash/Read/Write tool", no `mcp__` identifiers, no harness file locations. Say what to do ("read the file", "run the command"), not which product feature does it. Optional, harness-specific instructions go in a clearly separated appendix of `references/`, never in `SKILL.md`.

## 4. Scripts

- Language: Python 3 standard library first; R with packages named in the requirements; bash only for orchestration. A skill that needs a heavy dependency says so and keeps the offline tests independent of it where possible.
- A command-line program has a shebang, is executable, and `--help` exits 0 with usage. Libraries (files meant to be `source`d or imported) have no CLI and are documented in the header comment.
- Streams: data on stdout, logs and progress on stderr.
- Exit codes: 0 success; 1 unexpected error; 2 usage error; 3 a domain-specific "needs attention" outcome documented in `--help` (unresolved items, a pre-flight failure); 4 verification or audit failure. A script must never exit 0 after skipping work silently: unknown modes and missing inputs are errors.
- No network or system state at import time; no writes outside the paths given as arguments; no deletion of inputs.
- Scripts that start long or destructive work default to a dry run or print the commands (`--run` or an explicit runner to execute).
- Deterministic: seeds are arguments or fixed and logged.
- Portable: do not rely on GNU-only flags (`stat -c`, `md5sum` vs `md5`, `sed -i`), a particular locale, or a home directory layout.

## 5. Tests

- `tests/run.sh` runs everything offline, with no model and no network, from any working directory, and returns non-zero on failure. It finishes in minutes, not hours.
- Test the behaviour that was wrong once: each past failure of the real workflow becomes a test (a truncated download, a transposed matrix, a missing exon row).
- Fixtures are synthetic or tiny public excerpts; never real study data, never anything that identifies a person or an unpublished project.
- Where an equivalent trusted implementation exists, test against its output (golden files).
- Tests that need an optional tool (STAR, scDblFinder, poppler) are skipped with a printed reason when it is absent, and the skill says that path is then untested.
- Network endpoints that cannot be called in CI are exercised against recorded responses and a local server; the skill states that the live service is untested.

## 6. Publishing hygiene

- No private hostnames, user names, paths, e-mail addresses, tokens or IP addresses; no unpublished project names, sample names, or results. Keep a local, uncommitted list of project-specific strings in `.private-patterns` (one regular expression per line) or point `$SKILL_PRIVATE_PATTERNS` at it; the validator then fails on matches. Generic patterns (home paths, tokens, e-mail addresses, private IPs) are checked in CI.
- No caches, build output or files over 2 MB.
- Do not publish a number that you cannot trace to code that was run. If a result belongs to a specific dataset, leave it out or describe it qualitatively.
- Third-party material is cited with its licence; code ported from another language says so, and the equivalence test is kept.

## 7. Cross-model check (manual, before a release)

Mechanical checks do not prove that a different model follows the skill. For each new skill run this protocol with at least two different models or harnesses and record the outcome in the pull request:

1. Give the model only the skill folder and a one-paragraph task that the skill covers, with fixtures from `tests/`.
2. Do not help. Note every command the model runs, every place it deviates from `SKILL.md`, every question it asks.
3. Pass if it completes the task, the produced files match what `tests/` expects, and it does not invent flags. Any deviation caused by ambiguous wording is a bug in `SKILL.md`: fix the text, not the model.
4. Re-run the repository tests after any change.

## 8. Versioning

`plugin.json` carries the repository version. Add skills in a minor release; a change to a script's flags, outputs or exit codes is a breaking change and is listed in the pull request description.
